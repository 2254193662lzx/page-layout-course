🧩 贯穿案例：CourseHub 课程主页，从 v1 到 v2

🧩 Running case: The CourseHub landing page, v1 → v2

整门课只做一个案例：一门在线课程的主页 CourseHub。它的 v1 版本「能跑」，但在真实使用中暴露了 8 个布局问题。每一章先诊断其中几条，讲清背后的理论与浏览器规则，再用可交互的演示把它修好；第 6 章给出完整的 v1 → v2 对比与布局评审清单。

The whole course works on a single case: the landing page of an online course, CourseHub. Its v1 "works" — yet real usage exposed eight layout defects. Each chapter diagnoses a few of them, explains the underlying theory and browser rules, then fixes them in an interactive demo. Chapter 6 delivers the full v1 → v2 comparison and a layout review checklist.

编号# 布局病（v1 的症状）Layout defect (symptom in v1)
① ① 层次缺失：标题、正文、按钮统统 16px，用户 3 秒内找不到「立即报名」。 No hierarchy: headings, body text and the CTA button are all 16px, so users cannot find "Enroll" within 3 seconds.
② ② 间距无系统：21px / 13px / 37px 随手写，节奏混乱，元素间对不齐。 Arbitrary spacing: 21px, 13px, 37px written by hand; the rhythm is chaotic and edges stop lining up.
③ ③ 用绝对定位摆盒子：header 高度写死 120px，课程标题一长就压住下面的内容。 Absolute positioning: the header is hard-coded to 120px tall, so a longer course title overlaps the content below.
④ ④ 靠空格对齐导航：菜单项之间用 &nbsp; 和固定宽度撑开，文案一改就错位。 Space-hacked navigation: menu items are spaced with &nbsp; and fixed widths, so any copy change breaks the alignment.
⑤ ⑤ 卡片高度不齐：三张课程卡长短不一，图片和小屏下的长标题还会撑破容器。 Uneven cards: the three course cards differ in height, and images or long titles overflow their containers on small screens.
⑥ ⑥ 用 padding 假装网格：三栏靠左右 padding 凑出来，内容与网格对不齐，也无法跨列。 Fake grid: the three columns are faked with left/right padding, so content never lines up with the grid and items cannot span columns.
⑦ ⑦ 只做桌面端：320px 宽度下出现横向滚动条，点击目标小于 24px。 Desktop only: at 320px the page scrolls horizontally and tap targets fall below 24px.
⑧ ⑧ DOM 顺序与视觉顺序不一致：用 order 把侧栏挪到前面，键盘 Tab 顺序乱跳、屏幕阅读器读错。 DOM order ≠ visual order: order moves the sidebar first visually, so keyboard Tab order jumps around and screen readers read the wrong sequence.

为什么要用案例贯穿？布局知识最大的问题是「语法都会，一到真项目就用错」。把每个知识点都挂到同一个案例的具体症状上，你记住的就不是 display:flex 这个语法，而是「这种症状→这种布局算法→这种写法」的对应关系。

Why one running case? The real problem with layout knowledge is that people know the syntax but misapply it in real projects. By attaching every concept to a concrete symptom in one case, what you remember is not the syntax display:flex but the mapping "symptom → layout algorithm → idiom".

打开任一章节，左侧选小节，顶部切换 讲解 / 关键代码 / 演示，可以一边讲一边现场拖参数。快捷键：[ ] 切小节，1 2 3 切 tab。

Open a chapter, pick a section on the left, switch Explain / Key Code / Demo on top — you can drag the demo parameters live while lecturing. Shortcuts: [ ] for sections, 1 2 3 for tabs.

📖 学生自学

📖 Self study

每节的讲解 tab 都按「案例症状 → 理论依据 → 浏览器规则」推进；关键代码 tab 的 ⭐ 行就是必须记住的那几行，下面配「为什么这么写」与「有什么坑」。

The Explain tab always moves from case symptom → theoretical basis → browser rule. The ⭐ lines in Key Code are the ones to remember, each followed by "why write it this way" and "what breaks otherwise".

🔬 演示即实验

🔬 Demos as experiments

演示不是录屏，而是可操作的沙盒：调参、拖拽、注入超长文案做破坏性测试，并且实时显示浏览器的真实计算值（计算宽度、是否溢出、对齐偏差）。

Demos are not screencasts but operable sandboxes: tune parameters, drag things, inject absurdly long text to stress-test, and watch the browser’s real computed values (widths, overflow, alignment drift).

Switch languages at the top right, or append ?lang=en. Both languages are generated from the same structured source, so they stay strictly consistent — including code comments.

🎯 设计原则

🎯 Design principles

案例为中心，不是语法为中心。不单独罗列 API，而是每个知识点都回答一个问题：案例里的这个症状，用哪条浏览器规则来解决？为什么要这么做？不做会怎样？

Case-first, not syntax-first. No API dumps: every concept answers one question — which browser rule fixes this symptom in the case, why this way, and what happens otherwise.
