Chapter 5 Responsive and intrinsic layout

断点应该由内容决定，而不是由设备型号决定。更进一步：很多布局根本不需要断点。

Breakpoints should be decided by the content, not by device models. Better still: many layouts need no breakpoints at all.

5.1 断点由内容决定，而不是由设备决定

5.1 Breakpoints follow the content, not the device

「内容先崩」的那个宽度，才是你真正需要的断点。它可以被测量出来。

The width at which the content breaks is the breakpoint you actually need — and it can be measured.

先看一个有问题的做法：@media (max-width: 375px)、768px、1024px——这是把 iPhone、iPad 的设备宽度写成了断点。问题在于：①同一宽度下的设备千差万别（折叠屏、分屏、浏览器窗口只是被拖窄）；②你的内容不关心设备是什么，它只关心自己有多少空间。

Start with a problematic habit: @media (max-width: 375px), 768px, 1024px — device widths turned into breakpoints. Two problems: (1) devices at the same width differ endlessly (foldables, split screens, a desktop window simply dragged narrow); (2) your content does not care what the device is, only how much room it has.

🧠 理论支点：内容驱动断点（content-driven breakpoints）：把浏览器从宽到窄慢慢拖，盯着你的组件看，它第一次"看起来不对"的那个宽度就是断点。判断标准是具体的、可观察的：文字行长超过约 90 个字符（东亚文字约 45 个汉字）就难以阅读；卡片窄到标题要断成三行；两个按钮挤在一起；表格出现横向滚动。
这套方法把人从"猜设备"变成"测内容"，也自然带来了下一个推论：断点数量应该等于内容失败的次数，而不是约定俗成的 3 个。Andy Bell《Bootcamp》关于内容驱动断点；Ethan Marcotte 2010 提出响应式网页设计
🧠 Theory: Content-driven breakpoints: drag the browser from wide to narrow while watching your component. The width at which it first looks wrong is the breakpoint. The criteria are concrete and observable: line length beyond about 90 characters (roughly 45 CJK glyphs) becomes hard to read; a card narrow enough that the title wraps to three lines; two buttons colliding; a table growing a horizontal scrollbar. This turns "guess the device" into "measure the content", which yields the next corollary: the number of breakpoints should equal the number of times the content fails, not a conventional three.Andy Bell’s writing on content-driven breakpoints in Bootcamp; Ethan Marcotte coined responsive web design in 2010

移动优先：为什么顺序不能反过来

Mobile first: why the order matters

移动优先指先写窄屏样式（基础样式），再用 min-width 媒体查询逐步"增强"到宽屏。反过来写（先宽屏、再用 max-width 覆盖成窄屏）会带来三个具体问题：

Mobile first means writing narrow-screen styles as the base, then layering wider ones with min-width queries. Writing it the other way (wide first, then overriding down with max-width) causes three concrete problems:

  • 窄屏用户体验最差却写得最晚：最需要照顾的场景反而成为"补丁"。
  • 覆盖式 CSS 越写越乱：max-width 规则层层覆盖，最后没人敢删任何一行。
  • 单列布局的性能优势被浪费：窄屏的"单列 + 大间距"往往只需极少 CSS，作为基础样式最省代码。
  • The worst-served users are written last: the case needing most care becomes the patch.
  • Override CSS rots: max-width rules override one another until nobody dares delete a line.
  • It wastes the simplicity of single-column: the narrow layout usually needs very little CSS, so it makes the cheapest possible base.

怎么测量自己的断点？打开开发者工具，把视口宽度从 1440 慢慢拖到 320，每次停下来看：①有没有横向滚动条；②每行文字是不是长到读不下去；③有没有元素被压扁到失去可读性；④点击目标是不是小于 24×24px（WCAG 2.5.8）。把这四个"事故点"记下来，它们就是你的断点。5.1 的演示把这件事自动化了：拖动宽度滑杆，它会实时报告"内容在哪些宽度出问题"。

How to find your own breakpoints: open devtools and drag the viewport from 1440 down to 320, stopping to check four things: (1) is there a horizontal scrollbar; (2) are any lines too long to read; (3) is anything squashed past legibility; (4) are tap targets below 24×24px (WCAG 2.5.8). Note each failure width — those are your breakpoints. The 5.1 demo automates exactly this: drag the width slider and it reports where the content fails.

🧩 案例诊断：问题 ⑦ 只做桌面端v1 的设计稿只有 1440px 一版，实现时把所有尺寸都写成固定像素：容器 width: 1180px、侧栏 width: 280px、卡片 width: 360px。320px 屏幕上的结果：容器比屏幕宽 860px，出现横向滚动条；卡片被压到 320px 宽但内部 padding 还是 32px，文字只剩很窄一列；导航项之间的点击目标只有 16px 高。用 5.1 的探测器扫描一遍，可以量化地看到这些问题出现在哪些宽度。
🧩 Case diagnosis: defect ⑦ desktop onlyThe v1 design file has a single 1440px version, implemented with fixed pixels everywhere: container width: 1180px, sidebar width: 280px, cards width: 360px. On a 320px screen: the container is 860px wider than the screen, producing a horizontal scrollbar; cards are squeezed to 320px while keeping 32px of padding, leaving a very narrow column of text; nav targets are only 16px tall. The 5.1 detector quantifies which widths these failures occur at.

关键代码 ① 移动优先的骨架

Key code ① The mobile-first skeleton

基础样式 = 最窄屏；媒体查询只做"增强"，不做"修补"。

Base styles are the narrowest layout; queries only enhance, never patch.

/* ⭐ 关键点 ①：以下是不带任何媒体查询的基础样式 —— 单列、可伸缩 */
.container {
  width: min(100% - 2 * var(--space-4), 72rem);   /* ⭐ 用 min() 自带两侧留白与最大版心 */
  margin-inline: auto;
}
.card-wall {
  display: grid;
  grid-template-columns: minmax(0, 1fr);         /* 默认单列 */
  gap: var(--space-5);
}

/* ⭐ 关键点 ②：只在"内容需要"时才加断点，且用 min-width 往上增强 */
@media (min-width: 40rem) {                    /* 640px：两列才放得下卡片 */
  .card-wall { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}
@media (min-width: 64rem) {                    /* 1024px：可以容纳侧栏了 */
  .layout { grid-template-areas: "header header" "side main" "footer footer"; }
}

/* ⭐ 关键点 ③：断点值用 em，而不是 px —— 用户放大字号时断点会同步提前 */
@media (min-width: 40em) { /* 在用户字号 20px 时相当于 800px，布局不会"来不及换" */ }
/* ⭐ Key point ①: below is the base, with no media queries at all — single column, fluid */
.container {
  width: min(100% - 2 * var(--space-4), 72rem);   /* ⭐ min() gives side margins and a max width at once */
  margin-inline: auto;
}
.card-wall {
  display: grid;
  grid-template-columns: minmax(0, 1fr);         /* single column by default */
  gap: var(--space-5);
}

/* ⭐ Key point ②: add a breakpoint only when the content asks for it, and enhance upwards with min-width */
@media (min-width: 40rem) {                    /* 640px: two columns now fit */
  .card-wall { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}
@media (min-width: 64rem) {                    /* 1024px: a sidebar fits now */
  .layout { grid-template-areas: "header header" "side main" "footer footer"; }
}

/* ⭐ Key point ③: express breakpoints in em, not px — with a 20px user font size the breakpoint
   arrives earlier in pixels, so the layout is never caught out by zoom */
@media (min-width: 40em) { /* equals 800px at a 20px root font size */ }

关键点解释：为什么断点用 em？因为 em 在媒体查询里基准根字体大小，而根字体大小会随用户的浏览器字号设置变化。用户把默认字号从 16px 调到 20px 时，40rem 断点从 640px 变成 800px——布局会因为"文字变大、需要更多空间"而更早切换到宽屏方案，这正是我们要的联动。用 px 写断点则完全无视用户的字号选择。坑：rem 在媒体查询里同样基于根字号，效果与 em 一致，两者都可以；但不要混用，否则团队里会争论为什么"看起来一样的断点表现不同"。

Key point: Why em for breakpoints? Inside a media query em is based on the root font size, which follows the user’s browser font-size setting. When the user moves the default from 16px to 20px, a 40rem breakpoint moves from 640px to 800px — the layout switches to the wide variant earlier because the text needs more room, which is the coupling we want. Pixel breakpoints ignore that choice entirely. Pitfall: rem behaves the same as em in media queries, so either is fine — but do not mix them, or the team will argue about why two breakpoints "that look identical" behave differently.

关键代码 ② 让容器自己"知道"有多少空间

Key code ② Let the container know how much room it has

把"我有多宽"这件事从视口转移到容器，组件才能在任何地方复用。

Move "how wide am I" from the viewport to the container so a component can be reused anywhere.

.card-slot {
  /* ⭐ 关键点 ④：声明"这个元素要参与容器查询"，浏览器会为它建立尺寸容器 */
  container-type: inline-size;
  container-name: card;
}

/* ⭐ 关键点 ⑤：查询的是容器宽度，不是视口宽度 —— 同一个组件放进侧栏也会变窄版 */
@container card (max-width: 26rem) {
  .card { flex-direction: column; }
  .card__cover { width: 100%; }
}

/* 只在"响应自身宽度"时用容器查询；
   需要"整页换布局"（比如给 body 加一个类）时，媒体查询仍然是对的 */
@media (min-width: 64rem) { .site-nav { display: block; } }
.card-slot {
  /* ⭐ Key point ④: declare that this element participates in container queries */
  container-type: inline-size;
  container-name: card;
}

/* ⭐ Key point ⑤: query the container width, not the viewport — the same component in a
   sidebar picks the narrow variant on its own */
@container card (max-width: 26rem) {
  .card { flex-direction: column; }
  .card__cover { width: 100%; }
}

/* Use container queries to respond to a component’s own width;
   media queries remain correct for page-wide decisions such as adding a class to body */
@media (min-width: 64rem) { .site-nav { display: block; } }

关键点解释：container-type: inline-size 会让浏览器为这个元素建立尺寸容器，并且只跟踪行内轴（宽度）——因为跟踪块轴（高度）会导致循环依赖（内容高度影响容器高度，容器高度又影响内容布局）。坑：container-type 会让该元素成为"包含块"并影响其内部绝对定位元素、还会创建新的格式化上下文，所以不要随手加在最外层页面上，而是加在确实需要按自身宽度响应的可复用组件外层。

Key point: container-type: inline-size makes the browser treat the element as a size container and track only the inline axis (width) — tracking the block axis (height) would create a circular dependency, since content height affects container height which affects layout. Pitfall: container-type also makes the element a containing block for absolutely positioned descendants and creates a new formatting context, so do not sprinkle it on the page wrapper; put it on the outer element of a genuinely reusable component.

🎛️ 拖动宽度滑杆（320 → 1440），实时检测四类"内容失败"：横向溢出、行长过长、元素被压到不可读、点击目标过小。点"扫描全部宽度"会自动跑完整个区间，给出事故清单与断点建议。

🎛️ Drag the width slider from 320 to 1440 and watch four kinds of content failure being detected: horizontal overflow, over-long lines, elements squeezed past legibility, and undersized tap targets. "Scan all widths" runs the whole range and returns a failure list with breakpoint suggestions.

5.2 容器查询：让组件自己决定

5.2 Container queries: let the component decide

同一个卡片，放进侧栏它就该变成窄版。媒体查询做不到这件事，因为它只看视口。

The same card should take its narrow form inside a sidebar. Media queries cannot do that, because they only look at the viewport.

媒体查询问的是"屏幕有多宽"，容器查询问的是"我有多宽"。这个差别在组件复用时立刻显现：同一个课程卡片，出现在主区（800px）时应该是横排（左图右文），出现在侧栏（240px）时应该变成竖排（上图下文）。用媒体查询写，你只能得到"屏幕窄时全部变竖排"——主区里明明有空间，也跟着变竖排了。

A media query asks "how wide is the screen"; a container query asks "how wide am I". The difference shows up the moment a component is reused: the same course card should be a row (image left, text right) at 800px in the main area and a column (image above text) at 240px in a sidebar. With media queries you can only get "everything becomes a column when the screen is narrow" — including the card in the main area, which had plenty of room.

🧠 理论支点：容器查询是"组件级响应式"的技术基础。在它出现之前，设计系统里的组件只能有两种响应方式：①把断点交给使用者以参数形式传入（.card--narrow），②干脆不响应。前者把响应式责任推给了页面作者，后者让组件在窄容器里必然难看。容器查询把"我该用哪种形态"这件事收回给组件自己判断，组件的可移植性因此从"要读文档"变成"放进去就对"。CSS Containment Module Level 3 §3「Container Queries」；容器查询于 2023 年在三大引擎全部可用
🧠 Theory: Container queries are the technical basis of component-level responsiveness. Before them a design-system component had two options: pass the breakpoint in as a variant class (.card--narrow), or not respond at all. The first pushes the responsibility onto whoever uses the component; the second guarantees it looks wrong in a narrow container. Container queries return the decision to the component, so portability goes from "read the docs" to "drop it in and it works".CSS Containment Module Level 3 §3 "Container Queries"; container queries became available in all three engines in 2023

什么时候仍然该用媒体查询

When media queries remain the right tool

  • 影响整页的决定：侧栏是显示还是折叠、导航是横向还是抽屉、打印样式。
  • 与视口强相关的排版：例如整页标题的 clamp() 上下限（虽然 vw 单位更合适）。
  • 减少动画 / 降低数据用量等基于设备能力的查询（这些本来也不是尺寸问题）。
  • Page-wide decisions: is the sidebar shown or collapsed, is the nav horizontal or a drawer, print styles.
  • Typography tied to the viewport: page-level heading bounds in clamp() (though vw units are often better).
  • Device-capability queries such as reduced motion or lower data usage — those were never about size.

一条实用规则：如果一段响应式样式在"把组件搬到另一个容器里"之后仍然成立，那它应该用容器查询；如果它必须随整页变化（比如"手机上收起侧栏"），那它属于媒体查询。判断问题的方式不是问属性，而是问：这个变化是"我自己的空间"决定的，还是"整页环境"决定的？

A practical rule: if a responsive rule still makes sense after the component is moved into a different container, it belongs in a container query; if it must follow the whole page (as "collapse the sidebar on phones" does), it belongs in a media query. Ask not which property, but: is this change driven by my own space, or by the page environment?

🧩 案例诊断：同一个卡片，三种容器CourseHub v2 把课程卡做成了可复用组件，它出现在三个地方：主区卡片墙（每张约 340px）、详情页侧栏（约 260px）、以及页脚推荐位（约 180px）。用媒体查询时，这三个位置只能用同一个形态，因为视口宽度是一样的；换成 @container card (max-width: 26rem) 之后，侧栏与页脚里的卡片自动切换成竖排、封面占满宽度，而主区里的卡片保持横排。这就是"组件级响应式"省下的条件类数量。
🧩 Case diagnosis: one card, three containersCourseHub v2 turns the course card into a reusable component that appears in three places: the main card wall (about 340px each), a detail-page sidebar (about 260px) and a footer recommendation slot (about 180px). With media queries all three must share one form, because the viewport width is identical. With @container card (max-width: 26rem) the sidebar and footer cards switch to a column with a full-width cover while the main-area cards stay as rows. That is the number of variant classes component-level responsiveness removes.

关键代码 ① 一个组件，两种形态，零个变体类

Key code ① One component, two forms, zero variant classes

组件自己判断该用哪种形态，调用方不需要知道任何断点信息。

The component decides its own form; the caller needs to know nothing about breakpoints.

/* 组件内部：默认横排（宽容器形态） */
.card { display: flex; gap: var(--space-4); align-items: center; }

/* ⭐ 关键点 ①：给"容器"声明尺寸跟踪，名字便于阅读 */
.card-slot { container: card / inline-size; }

/* ⭐ 关键点 ②：窄容器形态 —— 竖排 + 封面占满
   cqw = 容器宽度的 1%，用它做"相对当前容器"的尺寸比 vw 更符合意图 */
@container card (max-width: 26rem) {
  .card { flex-direction: column; align-items: stretch; }
  .card__cover { width: 100%; height: auto; }
  .card__title { font-size: clamp(1rem, 4cqw, 1.25rem); }
}

/* ⭐ 关键点 ③：容器查询也支持范围语法，可读性更好 */
@container card (16rem <= width < 26rem) {
  .card__title { font-size: 1.05rem; }
}
/* inside the component: a row by default (the wide form) */
.card { display: flex; gap: var(--space-4); align-items: center; }

/* ⭐ Key point ①: declare size tracking on the container and name it for readability */
.card-slot { container: card / inline-size; }

/* ⭐ Key point ②: the narrow form — a column with a full-width cover.
   cqw = 1% of the container width: sizing relative to *this container* is more truthful than vw */
@container card (max-width: 26rem) {
  .card { flex-direction: column; align-items: stretch; }
  .card__cover { width: 100%; height: auto; }
  .card__title { font-size: clamp(1rem, 4cqw, 1.25rem); }
}

/* ⭐ Key point ③: container queries support range syntax, which reads better */
@container card (16rem <= width < 26rem) {
  .card__title { font-size: 1.05rem; }
}

关键点解释：注意 cqw 这个新单位：它表示容器宽度的 1%（还有 cqh、cqi、cqb、cqmin、cqmax）。用它做组件内部的流式尺寸，比 vw 更符合"相对我自己"的意图——一个放进对话框的卡片，用 vw 算出来的字号会完全跑偏。坑：cqw 必须在有尺寸容器的祖先里才有效，否则会回退到视口尺寸（或用小视口单位），排查时容易被误导。

Key point: Note the new cqw unit: 1% of the container’s width (alongside cqh, cqi, cqb, cqmin, cqmax). For fluid sizes inside a component it expresses "relative to me" far better than vw — a card inside a dialog sized with vw would be wildly off. Pitfall: cqw only resolves against a size container ancestor, otherwise it falls back to viewport units, which can mislead you when debugging.

关键代码 ② 迁移路径：从媒体查询到容器查询

Key code ② Migration path: media query to container query

不必一次全改：先加尺寸容器，再把"组件自身的响应"逐条搬过去。

No need to rewrite at once: add the size container first, then move the component’s own responses over one by one.

/* ⭐ 关键点 ①：第 1 步 —— 给可能变窄的容器加上尺寸跟踪 */
.card-wall, .detail__aside, .footer__picks { container-type: inline-size; }

/* 第 2 步：把"组件形态"的规则从 @media 搬到 @container */
/* ❌ 旧写法：屏幕窄 → 所有卡片竖排（主区明明还有空间） */
@media (max-width: 40rem) { .card { flex-direction: column; } }

/* ⭐ 关键点 ②：新写法 —— 卡片自己窄，它自己竖排 */
@container (max-width: 24rem) { .card { flex-direction: column; } }

/* ⭐ 关键点 ③：第 3 步 —— 整页级别的规则仍然留在 @media */
@media (max-width: 40rem) { .site-nav { display: none; } }   /* 导航收进抽屉，这是整页决定 */
/* ⭐ Key point ①: step 1 — add size tracking to containers that may become narrow */
.card-wall, .detail__aside, .footer__picks { container-type: inline-size; }

/* Step 2: move the component-shape rules from @media to @container */
/* ❌ old: narrow screen → every card becomes a column (even where there is room) */
@media (max-width: 40rem) { .card { flex-direction: column; } }

/* ⭐ Key point ②: new form — this card is narrow, so this card becomes a column */
@container (max-width: 24rem) { .card { flex-direction: column; } }

/* ⭐ Key point ③: step 3 — page-level rules stay in @media */
@media (max-width: 40rem) { .site-nav { display: none; } }   /* nav into a drawer: a page decision */

关键点解释：迁移时的性能与作用域注意点：container-type: inline-size 会让浏览器做额外的尺寸计算，在一个有几百个卡片的列表里全加上可能带来开销，所以只在真正需要按自身宽度变化的层级加（通常是组件外层，而不是每个卡片）。另外，旧浏览器不支持容器查询时会忽略 @container 块，因此要保证没有容器查询时布局也是可用的——这个思路叫渐进增强。

Key point: Performance and scope when migrating: container-type: inline-size costs the browser extra sizing work, so adding it to hundreds of cards in a list is wasteful — add it only at the level that genuinely needs to respond to its own width (usually the component wrapper, not every card). Also, browsers without container query support ignore @container blocks, so make sure the layout still works without them: that is progressive enhancement.

5.3 内在布局与流式排版

5.3 Intrinsic layout and fluid typography

最强的响应式布局是"没有断点的布局"：尺寸在内容与容器之间协商得出。

The strongest responsive layout is one with no breakpoints at all: sizes negotiated between content and container.

前面两节的断点与容器查询仍然是"在某个尺寸处切换方案"。内在布局（intrinsic layout）走向更进一步：让尺寸连续地随可用空间变化，不需要任何切换点。三个工具：clamp()（连续的尺寸插值）、内在尺寸关键字（min-content / max-content / auto）、以及基于 flex-basis 技巧的原语（primitive）。

Breakpoints and container queries still "switch plans at a size". Intrinsic layout goes further: sizes change continuously with the available space, with no switch point. Three tools: clamp() (continuous interpolation), the intrinsic sizing keywords (min-content / max-content / auto), and primitives built on a flex-basis trick.

流式排版的正确写法是"中间插值 + 两侧兜底"，而不是纯 vw：

The correct fluid-type idiom is "interpolate in the middle, bound both ends", not raw vw:

/* ❌ font-size: 4vw;  —— 窄屏小到读不了，宽屏大到失控 */
/* ✅ 两侧用 rem 兜底，中间用 vw 插值 */
h1 { font-size: clamp(1.75rem, 1.1rem + 2.4vw, 3rem); }

/* 更直观的写法：告诉浏览器"在 20rem 视口时 1.75rem，在 80rem 视口时 3rem" */
h1 { font-size: clamp(1.75rem, 1.75rem + (3 - 1.75) * (100vw - 20rem) / (80 - 20), 3rem); }
/* ❌ font-size: 4vw;  — unreadably small on phones, absurdly large on wide screens */
/* ✅ bound both ends in rem, interpolate in the middle with vw */
h1 { font-size: clamp(1.75rem, 1.1rem + 2.4vw, 3rem); }

/* A more explicit form: "1.75rem at a 20rem viewport, 3rem at 80rem" */
h1 { font-size: clamp(1.75rem, 1.75rem + (3 - 1.75) * (100vw - 20rem) / (80 - 20), 3rem); }

两难：流式排版 vs 用户缩放

The conflict: fluid type vs user zoom

流式排版有一个真实的冲突：它让字号"随视口变化"，而可访问性要求字号"随用户设置变化"（WCAG 1.4.4 要求文本能放大到 200% 而不丢失内容）。如果标题完全由 vw 决定，用户放大字号时它纹丝不动。解决办法有两个：①clamp() 的两端用 rem（用户字号变大时，上下限一起变大）；②只在装饰性的大标题上用强流式，正文与正文级标题保持纯粹的可缩放单位。

Fluid type has a genuine conflict: it makes size follow the viewport, while accessibility requires size to follow the user’s setting (WCAG 1.4.4 requires text to scale to 200% without loss of content). If a heading is governed purely by vw, increasing the user font size does nothing to it. Two fixes: (1) express the clamp() bounds in rem so the limits grow with the user’s font size; (2) use strong fluid scaling only for decorative large headings and keep body text and body-level headings in purely scalable units.

原语（primitive）：把布局写成可组合的小积木

Primitives: layout as composable building blocks

Every Layout 提出了一组极小的布局原语，每个原语只解决一个问题，并且不用断点：

关键代码 ① Switcher 原语：不写断点的横竖切换

Key code ① The Switcher primitive: row to column without a breakpoint

用一个 flex-basis 计算式，让"够宽就横排、不够就竖排"变成纯内在尺寸行为。

A single flex-basis computation turns "side by side when there is room, stacked when there is not" into pure intrinsic behaviour.

.switcher {
  display: flex;
  flex-wrap: wrap;                 /* ⭐ 允许换行，这是切换发生的地方 */
  gap: var(--space-4);
}

.switcher > * {
  /* ⭐ 关键点 ①：容器的"宽度阈值"参与计算。
     当容器宽度 > 阈值时为 -999×阈值（负值 → 被压缩成一行）
     当容器宽度 < 阈值时变为正的大值 → 每个子项独占一行（换行） */
  flex-grow: 1;
  flex-basis: calc((var(--switcher-threshold, 40rem) - 100%) * 999);
  min-width: 0;
}

/* 用法： <div class="switcher" style="--switcher-threshold: 34rem"> … </div>

/* ⭐ 关键点 ②：只对"四个以上"子项按需限制宽度，避免一行放太多 */
.switcher > :nth-last-child(n + 5),
.switcher > :nth-last-child(n + 5) ~ * { flex-basis: 100%; }
.switcher {
  display: flex;
  flex-wrap: wrap;                 /* ⭐ wrapping is where the switch happens */
  gap: var(--space-4);
}

.switcher > * {
  /* ⭐ Key point ①: the container width participates in the calculation.
     When the container is wider than the threshold this is a huge negative value, so items
     stay on one line; when it is narrower the value is large and positive, so each item
     takes a full line */
  flex-grow: 1;
  flex-basis: calc((var(--switcher-threshold, 40rem) - 100%) * 999);
  min-width: 0;
}

/* usage: <div class="switcher" style="--switcher-threshold: 34rem"> … </div>

/* ⭐ Key point ②: for five or more children, force extra items onto their own lines */
.switcher > :nth-last-child(n + 5),
.switcher > :nth-last-child(n + 5) ~ * { flex-basis: 100%; }

关键点解释：这个 calc() 技巧的关键在于"乘 999"：它把0 或 1 的二值判断放大成数值上不可忽略的量，从而让 flex 的换行机制去做"是否换行"的决定。坑：如果子项数量超过 4 个且不加以限制，flex 会把它们全部塞进一行（因为 flex-grow: 1 会收缩每一列），所以需要第二条规则限制每行数量。可读性：建议把阈值做成自定义属性（--switcher-threshold），让使用者一眼看出"这道线在哪里"。

Key point: The essential part of this calc() trick is multiplying by 999: it turns a binary yes/no into a numerically decisive value, letting the flex wrapping mechanism make the "wrap or not" decision. Pitfall: with more than four children and no limit, flex will cram them all onto one line (because flex-grow: 1 shrinks every column), which is why the second rule caps items per row. Readability: expose the threshold as a custom property (--switcher-threshold) so users can see where the line is.

关键代码 ② Stack 原语与流式版面宽度

Key code ② The Stack primitive and fluid measure

两个小原语，替代大量零散的 margin 与 width 声明。

Two small primitives replacing a pile of scattered margin and width declarations.

.stack > * + * {
  /* ⭐ 关键点 ③：相邻兄弟统一间距 —— 不用给每个子元素写 margin，
     也不会像 margin-bottom+margin-top 那样被折叠 */
  margin-block-start: var(--stack-space, var(--space-4));
}

/* ⭐ 关键点 ④：流式版心 —— 最小 100% - 两侧留白，最大 72rem，中间连续变化 */
.wrap {
  width: min(100% - 2 * var(--space-5), 72rem);
  margin-inline: auto;
}

/* ⭐ 关键点 ⑤：用 ch 单位限制行长，而不是限制宽度。
   65ch 是排版学里公认的舒适行宽（拉丁文），中英混排也适用 */
.prose { max-inline-size: 65ch; }

/* ⭐ 关键点 ⑥：内边距也参与流式，用 clamp 保持"小屏不挤、大屏不空" */
.section { padding-block: clamp(var(--space-6), 5vw, var(--space-9)); }
.stack > * + * {
  /* ⭐ Key point ③: one spacing for adjacent siblings — no margin on each child, and
     unlike margin-bottom plus margin-top it cannot collapse */
  margin-block-start: var(--stack-space, var(--space-4));
}

/* ⭐ Key point ④: fluid content width — at least 100% - side margins, at most 72rem */
.wrap {
  width: min(100% - 2 * var(--space-5), 72rem);
  margin-inline: auto;
}

/* ⭐ Key point ⑤: constrain the measure with ch, not with width.
   65ch is the conventional comfortable line length and works for mixed CJK/Latin too */
.prose { max-inline-size: 65ch; }

/* ⭐ Key point ⑥: padding can be fluid as well, keeping small screens tight and large ones roomy */
.section { padding-block: clamp(var(--space-6), 5vw, var(--space-9)); }

关键点解释：max-inline-size: 65ch 是"限制行长"的正解：宽度不是目的，行长才是。用固定 max-width: 720px 的做法在字号变化时行长就变了（用户放大字号 → 每行字数变少 → 反而更舒服；缩小字号 → 每行字数过多 → 难读）。用 ch 表达后，无论字号如何变化，行长都保持在舒适区间。坑：ch 基于 "0" 字形的宽度，中日韩字体的"0"与汉字宽度不同，所以中文排版习惯上用 max-inline-size: 40em 之类的写法更可控——但思路是一致的：约束行长，而不是约束像素宽度。

Key point: max-inline-size: 65ch is the correct way to constrain line length: the goal is the measure, not the width. A fixed max-width: 720px changes the measure whenever the font size changes (zoom in and the line gets fewer characters, which is comfortable; zoom out and the line gets too many, which is not). Expressing it in ch keeps the measure in the comfortable range at any size. Pitfall: ch is the width of the "0" glyph, and in CJK fonts that differs from the ideograph advance, so for Chinese text max-inline-size: 40em is often more predictable — but the principle is identical: constrain the measure, not a pixel width.
