6.1 阅读顺序 vs 视觉顺序

6.1 Reading order versus visual order

CSS 能自由改变视觉位置，但键盘用户和屏幕阅读器只看 DOM 顺序。这两者分叉的地方，就是可访问性事故的高发区。

CSS can move anything visually, but keyboard users and screen readers only see DOM order. Where the two diverge, accessibility breaks.

布局技术越强，"视觉顺序"与"DOM 顺序"就越容易分叉。分叉本身不是错误——错误的是把它用在影响阅读或操作顺序的地方。要理解这件事，先要看清三套"顺序"：

The more powerful the layout technique, the easier it is for visual order and DOM order to diverge. Divergence is not itself a mistake — the mistake is using it where it affects reading or operation order. To see why, separate three orders:

顺序由谁决定用户如何感知
DOM 顺序HTML 里元素的先后屏幕阅读器的朗读顺序；Tab 键的切换顺序；复制粘贴的顺序
视觉顺序CSS 决定的屏幕位置视力用户的阅读路径（左上 → 右下）
焦点顺序默认跟随 DOM 顺序（tabindex 可改）键盘用户的导航顺序
OrderDetermined byHow users perceive it
DOM orderThe sequence in the HTMLScreen-reader narration order, tab order, copy-paste order
Visual orderOn-screen positions decided by CSSThe reading path of sighted users (top-left → bottom-right)
Focus orderFollows DOM order by default (tabindex can change it)Navigation order for keyboard users

线性化（linearisation）是理解这一切的关键概念：屏幕阅读器会把页面压平成一个一维序列来朗读。所以只要视觉顺序与 DOM 顺序不同，视力用户和屏幕阅读器用户就获得了两份不同的信息——而其中一份是错的。

Linearisation is the key concept: a screen reader flattens the page into a one-dimensional sequence to read aloud. So whenever visual order differs from DOM order, sighted users and screen-reader users receive two different documents — and one of them is wrong.

🧠 理论支点：WCAG 2.4.3 焦点顺序（AA）要求：如果页面可以被顺序导航，焦点顺序必须保持含义与可操作性。换句话说：视觉上第 1、2、3 个东西，键盘上也应该是第 1、2、3 个。这条标准不禁止视觉重排，它只要求重排不要把语义搞乱。WCAG 2.2 · 2.4.3 Focus Order；MDN「CSS and accessibility: ordering」
🧠 Theory: WCAG 2.4.3 Focus Order (AA) requires that if a page can be navigated sequentially, the focus order preserves meaning and operability. In other words: if something is first, second, third visually, it should be first, second, third for the keyboard. The criterion does not forbid visual reordering; it requires that reordering does not scramble meaning.WCAG 2.2 · 2.4.3 Focus Order; MDN "CSS and accessibility: ordering"

三个常见陷阱

Three common traps

  • order 挪动交互元素：把"删除"按钮用 order: -1 挪到视觉最前面，键盘用户却要按到最后才碰到它。
  • row-reverse 处理"从右到左"：视觉上反了，Tab 顺序没反 → 焦点从右侧跳到左侧。正确做法是用 direction: rtl 或直接写对 DOM 顺序。
  • 用两套 DOM + display: none 切换布局：v1 的常见做法。它同时带来重复内容、状态不同步、以及"隐藏的那份仍可能被读到"的风险。
  • Moving interactive elements with order: an order: -1 delete button appears first visually but keyboard users reach it last.
  • row-reverse for right-to-left layouts: visually reversed but tab order is not, so focus jumps from right to left. Use direction: rtl, or simply write the DOM in the right order.
  • Two DOM copies toggled by display: none: a common v1 pattern. It brings duplicated content, state that drifts out of sync, and the risk that the hidden copy is still announced.

一条足够用的规则：让 DOM 顺序按最线性的那个版本写（通常是手机单列版，或"最重要优先"的顺序），然后用 Grid / Flex 在宽屏上做视觉重排。这样两个顺序在最重要的场景下天然一致，重排只发生在"空间充裕、肉眼可见"的情形里。第 4 章的 grid-template-areas 之所以被称为"布局契约"，正是因为它的使用方式天然符合这条规则。

A rule that is sufficient in practice: author DOM order for the most linear version (usually the phone single-column layout, or "most important first"), then reorder visually with grid or flex on wide screens. The two orders then agree by construction in the most critical scenario, and reordering only happens where there is visible space. This is exactly why grid-template-areas from Chapter 4 deserves the name "layout contract".

🧩 案例诊断：问题 ⑧ 用 order 挪动侧栏v1 为了让侧栏在桌面上出现在右边，给侧栏加了 order: 2、给主区加了 order: 1（DOM 里侧栏在前）。结果是：视觉上侧栏在右、主区在左（符合设计稿）；键盘上Tab 会先进入侧栏的搜索框和筛选器，再跳到主区，然后按视觉顺序回到右侧——用户会觉得"焦点在乱跳"，而屏幕阅读器会把侧栏读在正文之前，语义完全颠倒。v2 的做法是把 DOM 顺序改成"主区在前"（也就是手机版的阅读顺序），桌面端用 grid-template-areas 把侧栏放到右侧，两个顺序从此一致。
🧩 Case diagnosis: defect ⑧ moving the sidebar with orderTo put the sidebar on the right on desktop, v1 adds order: 2 to the sidebar and order: 1 to the main area (while the DOM has the sidebar first). The result: visually the sidebar is right and the main area left (matching the design); on the keyboard, Tab enters the sidebar’s search box and filters first, then jumps to the main area and back to the right — the focus appears to jump randomly — and a screen reader reads the sidebar before the body copy, inverting the semantics. The v2 fix is to put the main area first in the DOM (which is also the phone reading order) and place the sidebar on the right with grid-template-areas, so both orders agree.

关键代码 ① 用 Grid 重排，而不是用 order 打乱

Key code ① Reorder with grid, not with order

同样的视觉效果，一种写法破坏可访问性，另一种不会。差别只在于改的是"位置"还是"顺序"。

The same visual result: one implementation breaks accessibility, the other does not. The difference is whether you change position or sequence.

/* ❌ v1：DOM 里 side 在前，用 order 把它挤到右边 —— 焦点顺序跟着 DOM 走，于是乱跳 */
.layout { display: flex; }
.layout > .main { order: 1; }
.layout > .side { order: 2; }

/* ✅ v2：DOM 里 main 在前（= 手机阅读顺序），桌面端用 areas 放到右边 */
.layout {
  display: grid;
  grid-template-areas: "main side";
  grid-template-columns: minmax(0, 1fr) 15rem;
  gap: var(--space-6);
}
.layout > .main { grid-area: main; min-width: 0; }
.layout > .side { grid-area: side; }

/* DOM：
   <main class="main">…</main>
   <aside class="side">…</aside>     ← 侧栏在后，键盘在正文之后到达 */

/* ⭐ 关键点：手机单列时无需任何 CSS 改动 —— areas 换成单列即可，
   DOM 顺序始终是"正文 → 侧栏"，两个顺序永远一致 */
/* ❌ v1: side comes first in the DOM and order pushes it right — focus follows the DOM, so it jumps */
.layout { display: flex; }
.layout > .main { order: 1; }
.layout > .side { order: 2; }

/* ✅ v2: main comes first in the DOM (= the phone reading order); areas place the sidebar right on desktop */
.layout {
  display: grid;
  grid-template-areas: "main side";
  grid-template-columns: minmax(0, 1fr) 15rem;
  gap: var(--space-6);
}
.layout > .main { grid-area: main; min-width: 0; }
.layout > .side { grid-area: side; }

/* DOM:
   <main class="main">…</main>
   <aside class="side">…</aside>     ← sidebar later, so the keyboard reaches it after the body */

/* ⭐ Key point: the phone single-column layout needs no extra CSS — just switch the areas,
   and DOM order stays "body → sidebar", so the two orders never diverge */

关键点解释：为什么"改位置"比"改顺序"安全？因为 Grid 只改变元素画在哪里，不改变它在文档里的次序；而 order / row-reverse 改变的是布局算法内部的排序，于是视觉顺序与文档顺序同时被改写、彼此脱节。经验法则：需要在多个屏幕尺寸下切换顺序时，用 Grid 的 areas；只为了"微调位置"时，用 margin 或对齐属性，别动顺序。

Key point: Why is changing position safer than changing sequence? Grid only changes where an element is painted, not when it occurs in the document; order and row-reverse change the ordering inside the layout algorithm, so the visual order is rewritten while the document order is not, and the two come apart. Rule of thumb: switch order across screen sizes with grid areas; for pure positioning use margins or alignment properties and leave sequence alone.

关键代码 ② 让隐藏的内容真的"消失"

Key code ② Make hidden content actually disappear

响应式布局经常要"藏起一部分"，藏的方式决定了它会不会被读到、会不会被 Tab 到。

Responsive layouts constantly hide things; how you hide decides whether it is still announced or still focusable.

/* ❌ 位移出屏幕：内容仍然在可访问性树里，Tab 仍能聚焦，屏幕阅读器仍会朗读 */
.offscreen { position: absolute; left: -9999px; }

/* ❌ 高度为 0 + overflow hidden：有些辅助技术仍会读到 */
.collapsed { height: 0; overflow: hidden; }

/* ✅ 真正移除：display: none（从可访问性树中移除，不可聚焦） */
.hidden { display: none; }

/* ✅ 视觉隐藏但保留给屏幕阅读器（用于"跳到主内容"这类链接） */
.sr-only {
  position: absolute;
  width: 1px; height: 1px;
  padding: 0; margin: -1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
  border: 0;
}

/* ⭐ 关键点：响应式隐藏要"成对"——宽屏藏掉的导航，窄屏必须有等价入口 */
@media (min-width: 64rem) { .nav-drawer-toggle { display: none; } }
/* ❌ Pushed off-screen: still in the accessibility tree, still focusable, still announced */
.offscreen { position: absolute; left: -9999px; }

/* ❌ Zero height with overflow hidden: some assistive tech still reads it */
.collapsed { height: 0; overflow: hidden; }

/* ✅ Truly removed: display: none (out of the accessibility tree, not focusable) */
.hidden { display: none; }

/* ✅ Visually hidden but available to screen readers (for a "skip to content" link) */
.sr-only {
  position: absolute;
  width: 1px; height: 1px;
  padding: 0; margin: -1px;
  overflow: hidden;
  clip-path: inset(50%);
  white-space: nowrap;
  border: 0;
}

/* ⭐ Key point: responsive hiding must come in pairs — whatever the wide layout hides,
   the narrow layout must offer an equivalent route to */
@media (min-width: 64rem) { .nav-drawer-toggle { display: none; } }

关键点解释：.sr-only 这个模式值得记住：它是"给屏幕阅读器的，不给眼睛的"内容。典型用法是页面开头的"跳到主要内容"链接（键盘用户按 Tab 第一下就能跳过导航），以及图标按钮的文本标签。坑：不要用它来"藏"不应该存在的内容——如果一段内容对辅助技术也毫无意义（比如纯装饰图形），正确的做法是 aria-hidden="true" 加空 alt，而不是视觉隐藏。

Key point: The .sr-only pattern is worth remembering: content for screen readers but not for the eyes. Typical uses are a "skip to content" link at the top of the page (one Tab press lets keyboard users bypass the navigation) and text labels for icon buttons. Pitfall: do not use it to hide content that should not exist at all — if something is meaningless to assistive tech too (a purely decorative graphic), the correct answer is aria-hidden="true" with an empty alt, not visual hiding.

🎛️ 切换"用 order 强改顺序"与"用 grid 重排"，实时对比三套顺序（DOM 顺序 / 视觉顺序 / 焦点顺序）；点"播放 Tab 顺序"会真的依次聚焦每个元素，看焦点是否与视觉顺序一致。

🎛️ Switch between "reorder with order" and "reorder with grid" and compare three orders live: DOM order, visual order and focus order. "Play tab order" really focuses each element in turn so you can see whether focus follows what you see.

6.2 缩放、重排与可访问性的硬指标

6.2 Zoom, reflow and the hard accessibility criteria

四条可以自动化检查的标准：Reflow、Resize Text、Text Spacing、Target Size。它们把"布局好不好"变成"能不能通过"。

Four criteria you can check automatically: Reflow, Resize Text, Text Spacing and Target Size. They turn "is this layout good" into "does it pass".

布局的可访问性问题大多不是"能不能用"，而是在特定条件下能不能用：放大到 200% 字号、把视口压到 320px、用户用了自定义的文本间距、用户强制使用高对比度模式。WCAG 把这些条件写成了可测的标准，于是布局有了明确的验收线。

Layout accessibility problems are rarely about "does it work" and almost always about whether it still works under specific conditions: 200% text, a 320px viewport, a user’s custom text spacing, forced high-contrast mode. WCAG turns those conditions into testable criteria, which gives layout a concrete acceptance line.

标准要求怎么测布局上怎么满足

🧠 理论支点：为什么是 320px？因为 1280px 的视口放大到 400% 时，逻辑宽度正好是 320px——也就是说 320px 这一条标准实际上在保护低视力用户使用桌面浏览器放大的场景，而不仅是小屏手机。同理，"200% 字号"保护的是把系统默认字号调大的用户（这在低视力与老年用户中非常普遍）。这些标准的共同点：它们都在测试"当用户改变了某个默认值之后，你的布局还在不在"。WCAG 2.2 1.4.10 / 1.4.4 / 1.4.12 / 2.5.8；W3C《Understanding Success Criterion 1.4.10 Reflow》
🧠 Theory: Why 320px? Because a 1280px viewport at 400% zoom has a logical width of exactly 320px — so this criterion protects low-vision desktop users who zoom, not just small phones. Likewise, "200% text" protects users who raise their system font size, which is very common among low-vision and older users. 把可访问性检查变成构建流程的一部分。这四条标准都可以自动化：横向溢出用 scrollWidth > clientWidth 检测、点击目标量 getBoundingClientRect()、文本间距用注入样式表检测、放大用根字号变化检测。6.2 的演示把这四条做成了一个"压力测试台"，你可以先在自己的页面上跑一遍，再决定哪里需要改。

Make accessibility checks part of the build. All four criteria can be automated: horizontal overflow via scrollWidth > clientWidth, target size via getBoundingClientRect(), text spacing via an injected stylesheet, and zoom via a root font-size change. The 6.2 demo assembles them into a stress-test bench you can run against your own page before deciding what to fix.

🧩 案例诊断：v1 的四条标准全部不合格用 6.2 的压力测试台跑 CourseHub v1：1.4.10 在 320px 下横向溢出 860px（固定宽度容器）；1.4.4 根字号调到 32px 后卡片标题被两行截断（固定行高）；1.4.12 注入文本间距后导航项重叠（固定高度导航）；2.5.8 导航链接高 18px（只有内边距 2px）。四条全部不合格。v2 用第 2–5 章的手段逐条修复，压力测试台全部通过。
🧩 Case diagnosis: v1 fails all four criteriaRunning the 6.2 bench against CourseHub v1: 1.4.10 overflows horizontally by 860px at 320px (fixed-width container); 1.4.4 at a 32px root font size the card titles are clipped to two lines (fixed line height); 1.4.12 with injected text spacing the nav items overlap (fixed-height nav); 2.5.8 nav links are 18px tall (only 2px of padding). All four fail. Version 2 fixes them with the techniques from Chapters 2–5 and passes the whole bench.

关键代码 ① 一行 CSS：让布局能扛住用户的自定义

Key code ① One line that makes layouts survive user overrides

对抗"用户把我的样式改了"的最好办法，是一开始就不写脆弱的样式。

The best defence against "the user changed my styles" is to avoid brittle styles in the first place.

/* ⭐ 关键点 ①：文本容器永远不要写死高度 —— 这是 1.4.4 与 1.4.12 的共同底线 */
.card__title { min-height: 0; }        /* 允许它长高 */
.truncate-2 { -webkit-line-clamp: 2; } /* 如果确实要截断，明确写出来并给出 title 属性 */

/* ⭐ 关键点 ②：字号与间距全部用相对单位，用户的根字号设置才能生效 */
:root { font-size: 100%; }             /* 不要写 font-size: 16px —— 那会锁定用户设置 */
h1 { font-size: clamp(1.75rem, 1.1rem + 2.4vw, 3rem); }
.section { padding-block: clamp(2rem, 5vw, 4rem); }

/* ⭐ 关键点 ③：给所有可点击元素一个"物理下限"的点击区域（2.5.8） */
a.inline-link, .icon-btn {
  display: inline-flex;
  align-items: center;
  min-height: 24px;                    /* AA；移动端建议 44px */
  padding-block: 6px;
}
.icon-btn { min-width: 24px; justify-content: center; }

/* ⭐ 关键点 ④：长内容永远不要撑破容器（1.4.10 的地板） */
* { min-width: 0; }
img, video, table { max-width: 100%; }
/* ⭐ Key point ①: never give a text container a fixed height — the shared floor of 1.4.4 and 1.4.12 */
.card__title { min-height: 0; }        /* let it grow */
.truncate-2 { -webkit-line-clamp: 2; } /* if you really must clip, do it explicitly and add a title attribute */

/* ⭐ Key point ②: express type and spacing in relative units so the user’s root font size applies */
:root { font-size: 100%; }             /* never font-size: 16px — that locks the user’s setting */
h1 { font-size: clamp(1.75rem, 1.1rem + 2.4vw, 3rem); }
.section { padding-block: clamp(2rem, 5vw, 4rem); }

/* ⭐ Key point ③: give every clickable thing a physical minimum target (2.5.8) */
a.inline-link, .icon-btn {
  display: inline-flex;
  align-items: center;
  min-height: 24px;                    /* AA; 44px is recommended on touch */
  padding-block: 6px;
}
.icon-btn { min-width: 24px; justify-content: center; }

/* ⭐ Key point ④: long content must never break the container (the floor of 1.4.10) */
* { min-width: 0; }
img, video, table { max-width: 100%; }

关键点解释：关于 * { min-width: 0 }：这是一个有争议但有效的全局兜底。它解决的是第 3 章那个 flex/grid 项目的隐含最小尺寸问题，代价是可能让某些确实需要"最小内容宽度"的元素被压得过窄。更精确的做法是只在可能装长内容的容器上加（卡片、列表项、td）。关于 :root { font-size: 100% }：它把根字号交还给用户设置；如果你写 16px，用户把系统字号调到 20px 时页面纹丝不动——这正是 1.4.4 想避免的情况。

Key point: On * { min-width: 0 }: a debatable but effective global floor. It solves the implicit minimum size of flex and grid items from Chapter 3, at the cost of letting some elements be squeezed narrower than they need. More precise: apply it only to containers that may hold long content (cards, list items, td). On :root { font-size: 100% }: it hands the root size back to the user’s setting. Writing 16px means a user who sets 20px sees no change at all — exactly what 1.4.4 exists to prevent.

// ⭐ 关键点 ①：横向溢出（WCAG 1.4.10）—— 在 320px 容器里量
function checkReflow(root) {
  const before = root.style.width;
  root.style.width = '320px';
  const doc = root.ownerDocument.scrollingElement;
  const overflow = doc.scrollWidth - doc.clientWidth;   // > 0 即不合格
  root.style.width = before;
  return overflow <= 1;
}

// ⭐ 关键点 ②：点击目标尺寸（WCAG 2.5.8）
function checkTargets(root, min = 24) {
  return Array.from(root.querySelectorAll('a, button, input, select'))
    .filter(el => el.offsetParent !== null)              // 只看可见元素
    .map(el => { const r = el.getBoundingClientRect(); return { el, w: r.width, h: r.height }; })
    .filter(t => t.h < min || t.w < min);                // 返回不合格清单
}

// ⭐ 关键点 ③：文本间距（WCAG 1.4.12）—— 注入样式后看是否溢出
function checkTextSpacing(root) {
  const s = document.createElement('style');
  s.textContent = '* { line-height: 1.5 !important; letter-spacing: 0.12em !important;' +
                  '    word-spacing: 0.16em !important; } p { margin-block-end: 2em !important; }';
  document.head.append(s);

    .filter(el => el.scrollHeight > el.clientHeight + 2 && getComputedStyle(el).overflow !== 'visible');
  s.remove();

}

关键点解释：这三个函数是"布局的可访问性单测"。把它们接进 CI（比如在 Playwright 里跑一遍），任何"顺手加了个固定高度"的提交都会立刻被发现。坑：checkReflow 里把宽度设成 320px 只对局部容器有意义；如果要测整个页面，应该用浏览器视口（page.setViewportSize），因为媒体查询会参与布局，而在一个 320px 的 div 里媒体查询并不会变。这是 6.2 演示里两种模式的区别（测试的是组件还是整页）。

Key point: These three functions are unit tests for layout accessibility. Wiring them into CI (running them in Playwright, say) means a stray fixed height gets caught in the next commit.   1. Hierarchy: squint at the first screen — can you say what is most important within three seconds?
  2. Spacing: is there any value that is not on the spacing scale? Is between-group spacing clearly larger than within-group?
  3. Flexibility: double the longest piece of copy — does the layout still hold?
  4. Content-driven: are there fixed container widths or heights? Does 320px produce a horizontal scrollbar?
  5. Two-dimensional alignment: do elements in a section share alignment lines? Can you see the grid edges?
  6. Accessibility: tab through — does focus follow visual order? Does 200% zoom lose content? Are targets at least 24px?
  7. Maintainability: how many places must change when one element is removed? More than two means a fact is described twice.

整套课程的一句话总结：布局的本质是"把信息结构翻译成空间结构"。浏览器提供了两套翻译机制：一维的流动（正常流、Flex）与二维的网格（Grid）；而判断"翻译得好不好"的标准不是好看，而是它在内容变化、屏幕变化、用户状态变化时，是否仍然成立。

The whole course in one sentence: layout is the translation of information structure into spatial structure. // ⭐ 关键点 ①：一次性跑完"布局评审清单"的自动化部分
export function reviewLayout(page) {
  return page.evaluate(() => {
    const issues = [];
    const seen = new Set();

    // (1) 横向溢出（WCAG 1.4.10）
    const doc = document.scrollingElement;
    if (doc.scrollWidth - doc.clientWidth > 1) issues.push('reflow: 横向溢出 ' + (doc.scrollWidth - doc.clientWidth) + 'px');

    // (2) 点击目标（WCAG 2.5.8）
    document.querySelectorAll('a, button, input, select').forEach((el) => {
      if (!el.offsetParent) return;
      const r = el.getBoundingClientRect();
      if (r.height < 24 || r.width < 24) issues.push('target: ' + (el.textContent || el.tagName).trim().slice(0, 18) + ' ' + Math.round(r.width) + '×' + Math.round(r.height));
    });

    // (3) 绝对定位的布局元素（第 2 章：只该用于装饰）
    document.querySelectorAll('header, nav, main, aside, section, article').forEach((el) => {
      if (getComputedStyle(el).position === 'absolute') issues.push('absolute: ' + el.tagName.toLowerCase() + ' 用绝对定位参与布局');
    });

    // (4) 不在 8pt 尺度上的间距（第 1 章）
    document.querySelectorAll('*').forEach((el) => {
      const cs = getComputedStyle(el);
      ['rowGap', 'columnGap'].forEach((p) => {
        const v = parseFloat(cs[p]);
        if (v > 0 && v % 4 !== 0 && !seen.has(el)) { seen.add(el); issues.push('spacing: gap ' + v + 'px 不在 4pt 尺度上'); }
      });
    });
    return issues;
  });
}
